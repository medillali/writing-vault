# 小说工作室本地工作架构框架 V0.3

版本：0.3

日期：2026-09-12

状态：初版设计，可用于组织试运行；尚未实现自动化，也尚未验证生产效率。

## 1. 目标与依据

本框架依据《本土小说改编 V1.0》修改版白皮书、本地工作流讨论、工程化创作资料与《巴西网文增长策略》讨论修订。以 Character Cards 与 Story Bible 为核心，建立从原创设计、目标语言写作、审稿定稿到反馈复盘的文件工作流。V0.3 是当前完整框架，V0.1/V0.2 保留为历史版本；本版新增巴西文化重构、市场假设、阅读实验与数据回写规则，详见第20—26节。

第一阶段要证明：一部小说能够逐章产出，在更换会话后仍能恢复准确上下文，且人工编辑成本与问题来源可被记录。

白皮书中市场数据、平台合同和收入数字不作为本框架的已验证事实。实施发布前另行核查。本文只定义发布准备与反馈接口。

### 1.1 初版假设

- 小团队运行：负责人、故事编辑、目标语言母语编辑；前两项可以由同一人承担。
- 内部策划语言为中文，正文直接使用选定目标语言。
- 白皮书正文提出墨西哥优先的拉美西语路线，后续讨论转向巴西。本框架暂以巴西 `pt-BR` 为试运行假设，作品立项时必须明确；若选择墨西哥，则使用相应西语规范，不能沿用葡语规范。
- 文件保存在本地；这不表示模型离线运行。
- 首轮完成一部作品前5章，再决定扩大到多个概念或更长连载。
- 首轮受众暂按巴西18—24岁女性、手机阅读场景设计；这是试验范围，不表示该群体偏好一致。具体类型与发布渠道在作品立项时选择。

### 1.2 架构选择

| 方案 | 适用情况 | 取舍 |
|---|---|---|
| 本地文件工作台，初版采用 | 小团队、流程尚在调整 | 易阅读、易修改、易追溯；需要明确维护责任 |
| 文件加脚本 | 已有重复且稳定的机械操作 | 自动整理上下文、检查字段、导出稿件；需要维护脚本 |
| 数据库加工作流应用 | 多作品协作出现明确瓶颈 | 检索与统计更强，建设和维护成本更高 |

## 2. 总体架构

```mermaid
flowchart TD
    A[多来源类型研究与假设登记] --> A1[叙事功能提炼与巴西文化重构]
    A1 --> B[原创 Concept 与人工 Story Room]
    B --> C[角色卡与 Story Bible]
    C --> D[Arc 与章节任务]
    D --> E[本章上下文包与场景安排]
    E --> F[目标语言初稿]
    F --> G[人物与连续性审稿]
    G --> H[修改与语言编辑]
    H --> I[人工确认定稿]
    I --> J[事实变更核对与入库]
    J --> E
    J --> K[发布包与版本检查]
    K --> L[读者反馈与成本记录]
    L --> M[人工复盘与假设更新]
    M --> B
```

架构划分为五层：

| 层 | 职责 | 核心交付物 | 最终负责人 |
|---|---|---|---|
| 选题设计 | 定义读者、情绪承诺、原创冲突 | Concept、Story DNA 分析、决策记录 | 负责人 |
| 故事资产 | 约束人物、关系、世界和发展方向 | 角色卡、Bible、Arc | 故事编辑 |
| 章节生产 | 把已确定结构变成可读正文 | 章节任务、场景、初稿、审稿、定稿 | 故事编辑 |
| 状态与版本 | 维护已发生事实和版本依据 | 时间线、秘密表、关系状态、变更记录 | 故事编辑 |
| 发布与反馈 | 输出作品材料并记录实际反馈 | 发布包、反馈、生产成本、复盘 | 负责人 |

## 4. 核心故事资产

### 4.1 Concept

必填项：目标市场与语言、类型、目标读者、情绪承诺、核心人物冲突、故事独特之处、预期产品形态。

引用 market-brief 的受众与产品假设，并经 cultural-recasting 检查人物职业、资源、生活背景与冲突的因果关系。研究来源不直接进入正式写作上下文。

立项检查：能否说明人物为何必须行动，以及冲突如何持续发展。热门标签组合不能替代故事发动机。

### 4.2 Character Cards：三轮构建

1. 结构设计：身份、表层目标、深层需要、恐惧、缺陷、能力、资源、秘密、矛盾、压力反应、说话方式。
2. 关系压力测试：提出能够同时推动双方目标、又加剧关系冲突的事件，人工筛选。
3. 极端场景测试：检验人物面对羞辱、背叛、机会时是否具有可解释的一致性。

底线采用“默认不会做什么，以及突破底线所需的铺垫和代价”。人物成长必须有依据，不能将所有变化都判成漂移。

### 4.3 Story Bible

保留六项：Story Promise、Main Characters、Core Relationships、Story Engine、Transformation、Ending Direction。

Bible 定义长期约束，不复制每章细节。角色完整资料引用角色卡，实际发生事件引用 canon，减少重复维护。

### 4.4 辅助资产

| 对象 | 最小字段 | 更新时机 |
|---|---|---|
| Story DNA | 读者幻想、情绪承诺、权力关系、主冲突、回报循环、分析来源 | 选题及复盘 |
| Arc | 起始状态、目标、升级、转折、结束状态、预期范围 | 阶段设计与重大修改 |
| World Bible | 规则、适用范围、限制、首次使用依据 | 采用新规则时 |
| Timeline | 事件ID、故事时间、事件、人物、来源章节与场景 | 定稿后 |
| Secret Table | 秘密ID、真相、各方认知、获知依据、更新章节 | 定稿后 |
| Relationship State | 人物对、信任与利益状态、冲突、变化原因、来源 | 关系变化后 |
| Promise Ledger | 伏笔ID、实际埋设与推进、兑现依据、关联计划 | 定稿后 |

Arc 采用白皮书提出的15—25章作为规划参考，具体可调整。首轮只细化前5章，其余保持阶段级安排。

秘密认知区分“不知道、怀疑、确信、误以为”。读者也作为独立知情方；误解须写清错误信念。

## 5. 事实与计划的管理规则

### 5.1 三类信息分开

- 固定设定：人物核心、世界规则、叙述约束。
- 未来计划：Arc、未发生场景、预计揭密时间。
- 已发生事实：定稿中实际出现的事件、人物认知与关系变化。

计划揭密章节存于 outline，不能直接改写 canon 中的知情状态。

### 5.2 冲突处理

定稿正文是已发生事实的依据，摘要与表格是派生资料。两者冲突时，查定稿原文。

正文若与已批准设定冲突，必须由编辑决定修改正文或正式调整设定，并记录影响。不能以任一文件优先为由自动抹平冲突。

尚未定稿的情节不得进入正式 canon。没有查到依据时标记“未确认”，不能补写事实。

### 5.3 改稿传播

修改已定稿章节时记录旧版本、新版本、修改原因和受影响章节。重新提取 delta，修复相应 canon，并将依赖旧事实的后续章节标为“待复核”。

发布版本保留快照；本地改稿不能被视为平台版本已更新。

## 6. 逐章生产规程

| 步骤 | 输入 | 输出 | 通过条件 |
|---|---|---|---|
| 1. 人工定章 | Bible、Arc、上一章状态 | brief | 明确本章行动、变化、回报与保留信息 |
| 2. 准备上下文 | 相关角色、canon、旧章原文 | context | 来源与版本明确，重要事实有依据 |
| 3. 场景设计 | brief、context | beats | 行动与结果有因果，视角与时间合理 |
| 4. 正文写作 | 已确认场景、语言规范 | draft | 完成章节任务，新增设定另列提案 |
| 5. 故事审稿 | draft、约束与事实 | review | 人物、时间、秘密、规则问题均有证据 |
| 6. 修改及语言编辑 | 问题清单与正文 | 修订稿 | 结构问题处理，目标语言可自然阅读 |
| 7. 人工定稿 | 修订稿、已处理问题 | final | 编辑确认；语言编辑状态如实记录 |
| 8. 状态提交 | final、上一章 canon | delta 与更新后的 canon | 事实变更逐项核对并与定稿版本对应 |

章节任务至少包含：视角、目标、阻碍、行动、转折、Reader Reward、Exit Hook、允许揭露、必须保留、结束状态、关联伏笔ID、目标语言与篇幅单位。

场景卡补充地点、故事时间、出场人物、场景开始与结束状态。以简短概要或场景序列确认因果后，再扩写正文；概要与 beats 可以合并，避免重复填表。一次提交一章，长章可分场景起草后合并审查。篇幅按语言和产品设定：中文字符数与葡语/西语词数分开计量，不直接套用3000—5000中文字符的标准。逐章生成不能单独解决上下文遗漏，仍须执行上下文准备与检索。

上下文包包含全书简要约束、当前 Arc、本章相关人物、最新实际状态、上一章正文与相关旧章原文。未来情节单独标注“计划”。

新一章以已完成状态提交的上一章为基础。可以提前构思场景，但不能把未确认事实作为后续正文的基础。

### 6.1 章节状态

`planned → drafted → reviewed → revised → finalized → canon-synced`

审稿失败返回 drafted/revised；修改已定稿事实后，相关章节标记 needs-recheck。作品 project 文件记录最新完成章节及下一步。状态、当前稿件版本、已完成门禁与最后成功操作同步写入 checkpoint；恢复协议见第17节。

### 6.2 人工检查点

- 批准核心人物与 Bible。
- 确认重大桥段和章节场景安排。
- 确认定稿及其事实变化。
- 决定继续、重写、暂停或终止项目。

这些是编辑工作中的检查点，可以在批次评审中完成，不要求每次机械操作都重新征求许可。

## 7. AI任务模块与自动化边界

以下是逻辑模块设计，尚未创建或安装为可调用 Skill。

| 模块 | 输入与输出 | 边界 |
|---|---|---|
| CHARACTER_ARCHITECT | 人工原型 → 角色卡与压力测试 | 输出候选，不替代编辑选择 |
| STORY_BIBLE_COMPILER | 已采用决策 → Bible | 不把未采用提案写成正式设定 |
| CHAPTER_ARCHITECT | Arc、状态、章节目标 → brief 与 beats | 不越过既定揭密边界 |
| TARGET_LANGUAGE_WRITER | 场景、上下文、style → 正文 | 按作品语言运行，新增事实单列 |
| CHARACTER_GUARD | 正文、角色约束 → 问题证据 | 不直接重写人物 |
| CONTINUITY_GUARD | 正文、canon、相关旧文 → 矛盾报告 | 无依据时标记不确定 |
| STYLE_EDITOR | 已修复结构的正文、style → 语言修订 | 不擅改情节、视角或含义 |
| CANON_UPDATER | 定稿、旧状态 → delta 草案 | 确认后才写入正式状态 |
| PROMISE_AUDITOR | 伏笔计划、实际记录、正文 → 回收与超期检查 | 未写入正文不能判定已回收 |
| GATE_REVIEWER | 稿件版本、审稿结果 → 门禁记录 | 缺证据不能判定通过 |

每个模块统一记录：版本、输入要求、任务、约束、输出格式、失败条件、少量正反例。首轮先用普通文件任务指令验证，再固化为 Skill。

后续可自动化的机械动作：检查必填字段、章节编号、缺失引用、版本匹配、上下文整理、字数统计、文件导出。

故事 Hook 指叙事悬念；自动化 Hook 指流程触发动作。两者在文档中分开命名。确定性检查只能发现结构或文件问题，不能证明故事质量。

## 8. 质量与返工

| 级别 | 示例 | 处理 |
|---|---|---|
| 阻断问题 | 越权知情、重大时间矛盾、缺失关键动机 | 解决后才能定稿 |
| 重要问题 | 转折缺铺垫、章节无实际回报、人物反应缺解释 | 修改或记录保留理由 |
| 表达建议 | 重复表达、对白不自然、局部节奏 | 语言编辑处理 |

审稿记录格式：问题ID、位置、问题、依据、影响、建议、处理结果。单独的模型评分不能作为放行依据。

语言编辑后重新检查含义变化。母语编辑暂未参与的章节可以作为内部定稿，但发布包必须清楚记录该状态，不能标为已通过母语审核。

每轮同时检查：本章是否给出回报，悬念是否兑现或合理延后，人物是否有具体行动，是否反复解释同一情绪。不能把增加章节数当作质量目标。

## 9. 人员与日常协作

| 角色 | 负责事项 |
|---|---|
| 负责人 / Producer | 选题、资源投入、产品形态、阶段决策与发布 |
| Story Editor | 角色、Bible、Arc、逐章生产、canon、版本一致性 |
| Native Editor | 目标语言自然度、对白、文化合理性，标注含义变动 |
| AI | 提案、初稿、检索整理、审稿辅助和变更草案 |

建议每周一次 Story Room，讨论下一阶段关键场景、权力变化、秘密揭露与已出现的问题。每次只把采用结论写入 decisions，其余保留为候选。

日常从 project 文件恢复进度：确认版本与上一章状态，执行当前步骤，结束时记录完成项、未解决问题和下一步。依赖信息必须写入文件，不能只留在聊天里。

## 10. 发布与数据反馈接口

发布包包含：目标渠道与语言、标题、简介、类型标签、角色关系、样章、计划篇幅与更新方式、编辑状态、稿件版本。

渠道研究另行记录最新来源和核查日期。框架不预设签约成功、收益分成或发布资格。

| 数据 | 记录口径 |
|---|---|
| 单章生产成本 | 实际模型费用、编辑费用及分摊方式；订阅无法精确归因时标注估算 |
| 人工编辑时间 | 分开记录故事修改与语言修改时间 |
| 返工 | 问题类别、发生环节、处理轮次 |
| 阅读反馈 | 渠道、时间范围、版本、样本量、原始反馈 |
| 留存与转化 | 仅使用可获得且口径明确的数据；缺失记为未提供，不填零 |

连载和整本书采用不同交付标准。前5章可用于样章测试，不能被当作完整长篇成品。小样本反馈形成下一轮假设，不直接宣称市场结论。

## 11. 试运行阶段与验收

### 阶段 A：建立最小资料

交付：一份 Concept、核心角色卡、精简 Bible、第一 Arc、语言规范与初始状态。

验收：核心冲突可以持续发展，目标语言明确，主要人物行为可解释。

### 阶段 B：完成第一章闭环

交付：brief、context、beats、draft、review、final、delta 与更新后的 canon。

验收：定稿与状态对应，问题处理可追溯；必要字段确实被使用。

### 阶段 C：连续完成前5章

交付：5章内部定稿、各章变更、问题与工时记录。

验收：阻断问题已解决，人物知情有依据，章节有实际变化，语言审核状态真实。

### 阶段 D：独立恢复与第6章规划

以本地文件重新构建上下文，恢复主要人物目标、秘密状态、未完成伏笔与当前时间，再规划第6章。

验收：恢复过程不依赖历史聊天补充关键事实；发现缺口时修订资料组织方式。

### 阶段 E：决定扩展

结合人工耗时、返工类型和目标读者反馈，选择继续到10—30章、重写前段或暂停。再逐步回到白皮书的多 Concept 筛选机制。

初版不设虚构效率或收益指标。首轮记录形成基线后，再设可检验的改进目标。

## 15. 伏笔与读者承诺台账

秘密表回答“谁知道什么”，伏笔表回答“向读者许诺了什么、是否兑现”。两者用ID关联，不能相互替代。事业目标、物件用途与关系修复等承诺也可能没有秘密。

### 15.1 两份资料与三级范围

- outline/promises-plan：伏笔ID、全书/Arc/局部范围、叙事目的、计划埋设、预计回收窗口、延期原因与批准决策。
- canon/promises：伏笔ID、实际埋设来源、推进来源、实际回收来源、当前状态、关联人物/秘密ID。

范围表示叙事跨度，不自动决定固定章节期限。每条承诺单独设定回收窗口；全书级承诺可设 Arc 级推进检查点。

计划状态为 planned；进入定稿后，实际状态为 planted、advanced、paid-off 或 retired。retired 必须记录处理理由；若读者已看到明确承诺，应设计合理收束，不能只删除表格行。

### 15.2 写前、定稿后与全局检查

写前列出本章应推进的承诺、临近窗口的承诺，以及尚无推进记录的全书承诺。定稿后依据原文登记真实变化。

超过回收窗口产生“待处理”提醒，由编辑决定回收、延后或调整结构。不能为了清除提醒强行插入回收。计划窗口修改保留旧值与原因。

每5章、每个 Arc 结束及重大改稿后，检查未兑现承诺、假回收、重复回收、揭密与角色认知矛盾。首轮第5章必须执行一次。

示例：P-003“女主为何一直保存钥匙”在第2章场景S02埋设，计划在第6—8章说明用途。第7章只再次提到钥匙，应记为推进；实际用途改变人物行动后，才根据原文判断是否兑现。

## 16. 六道质量门禁与风格规程

六道门禁覆盖第6节已有生产步骤，不要求重复进行六次独立模型调用。一次审核可以覆盖多个检查面，但结果按门禁记录。

| 门禁 | 检查 | 放行条件 |
|---|---|---|
| G1 输入完整 | 当前约束、上下文、来源版本、章纲 | 缺失的关键事实得到补齐或明确避开 |
| G2 因果与人物 | 场景目标、行动、转折、动机 | 阻断问题清零，重要问题有处理记录 |
| G3 连续性与承诺 | 时间、知识、世界规则、伏笔 | 冲突有双向来源，未解决的阻断项为零 |
| G4 节奏与语言 | 回报、拖延、对白、风格、修改后含义 | 无虚假回报；重要语言问题已处理 |
| G5 人工定稿 | 最终稿件、审稿结果、语言审核状态 | 人工确认对应版本；不能伪造母语审核 |
| G6 状态与输出 | delta、canon、索引、导出版本 | 状态提交完整，正文与派生资料一致 |

G1在写前，G2—G4在草稿与修订阶段，G5对应定稿，G6对应状态提交。G6完成前不得启动依赖本章事实的下一章正文或正式导出。

gate 必填：章节ID、稿件版本、检查时间、审阅者/任务模块、各门禁结果、问题ID、来源、下一步。结果分 pass、fail、needs-human；条件不适用时写明理由。正文修改后重新执行受影响门禁，旧版本的通过记录不能直接沿用。

同一阻断问题连续两轮未解决，停止自动润色，回到场景、章纲或设定层处理。这是首轮可调整的操作阈值，不是行业标准。

### 16.1 两遍语言编辑

第一遍：修复空泛抽象、模板化反应、重复情绪说明、声音同质化、无目的对白与冗余总结。依据作品 style 和当前场景进行局部修改，避免统一替换词语。

第二遍：对照修订前后，检查事实、否定、时间、视角、人物意图、情绪强度和伏笔是否被改变。发现含义变化则重新进入相关故事门禁。

不承诺“AI检测通过率”，也不把检测分数作为质量指标。目标是更自然、有具体人物行动且保持含义的正文。

### 16.2 风格资产

style 记录叙述距离、时态、句段节奏、对白比例倾向、意象密度、情绪表达方式、各角色声音、目标语言习惯与少量原创正反例。参数是编辑参考，不是每章必须满足的机械配额。

从多样参考中归纳可观察的叙事特征，形成作品自己的规则；不把某位作者的姓名作为执行标准。参考来源与分析保留在研究资料中，生产上下文使用已批准的风格规则与自有示例。

## 17. 断点恢复与受控变更

### 17.1 恢复检查点

checkpoint 最小字段：作品ID、章节ID、当前阶段、当前正文版本、Bible/Arc版本、canon覆盖至哪章、最近完成门禁、待解决问题、下一步、最近成功操作ID。

版本可先用明确修订号及Git版本记录；自动化后再补内容哈希。文件存在本身不代表阶段完成。

恢复顺序：读取 project 与 checkpoint，核对实际文件及版本，检查最后门禁，从最后成功步骤之后继续。发现文件与记录不符，先核对差异，不能直接追加正文或重复更新事实。

### 17.2 状态提交中断

delta 记录基线版本、目标定稿版本、变更ID及每项应用状态。若正文已定稿但 canon 只更新一部分，先完成或撤回该次状态提交，再将章节标记 canon-synced。

同一个变更ID只应用一次；若定稿版本已改变，旧delta失效，须重新提取。初版由编辑按清单核对，未来再实现自动检查，当前不宣称具备原子写入或自动恢复能力。

### 17.3 改纲与改设定

提出变更原因 → 列出受影响约束、章节和伏笔 → 编辑确认 → 更新规划版本 → 标记依赖章节待复核 → 修订及重新过门禁。

局部措辞和不改变事实的语言调整可在编辑职责内完成；改变主线、结局、人物核心动机或已发布事实时，交负责人决定。默认遵守当前章纲，但允许经记录的创作调整。

## 18. 记忆检索与协作升级条件

“五层协同记忆”包含存储、检索和审核等不同职能。本项目明确分为：

1. 权威资料：当前设定、规划与定稿原文，各司其职。
2. 派生索引：canon、摘要与伏笔记录，均有原文依据。
3. 本章检索：按人物、事件、秘密和伏笔ID找到相关片段，记录来源版本。
4. 输入约束：本章任务和禁止提前揭露的信息。
5. 审核：比对输出与约束，标注冲突与不确定性。

初版用目录、ID和关键词检索。检索不到不等于事实不存在，需检查别名及相关章节；仍不确定则提出资料缺口。未来采用RAG也必须保留来源，不能把检索结果当作完整事实集合。

当反复漏检旧章且人工检索耗时成为明确问题时，再试验向量检索；当关系查询超出表格能力时，再考虑图结构。引入前后比较同一组事实查询的准确性和人工时间。

角色分工不等于必须同时运行多个Agent。初版按策划、写作、审核顺序执行；如启用独立审核，审核方只输出问题报告，故事编辑负责合并修改。多个角色不同时写canon或同一正文，前后依赖章节默认串行。不同Agent可能共享错误，多数赞成不能替代原文依据。

## 21. 来源研究到原创立项

### 21.1 研究与生产的输入边界

研究侧可保留作品名称、来源链接、阅读范围、研究者、日期和不确定性。没有读到原文的细节不能凭模型记忆补齐；只读简介时标明“简介分析”。

Source DNA Card抽取：读者幻想、人物吸引力、核心母题、权力差、双方情感缺口、开局功能、靠近机制、情绪承诺、中段回报功能、危机功能、最终回报功能。记录叙事功能，避免把单一作品的完整事件序列包装成抽象模板。

生产侧只接收人工选择的抽象机制、原创角色、世界规则、章纲与风格约束。参考书名用于研究溯源，不用作“按这本书写”的生成指令。

项目默认沿用白皮书的原创路线。正式授权改编应单独建立项目与授权范围记录，不能混用本框架的原创标记。更名、换地点或降低文字相似度都不能证明新作品已经独立原创。

### 21.2 文化迁移卡

每个待迁移元素记录：原叙事功能、KEEP/REBUILD/DROP决策、原创实现、生活依据、尚未解决的问题。

KEEP保留的是抽象情绪或冲突功能；REBUILD重新设计实现该功能的制度与行动；DROP删除不再服务新故事的元素。例如，升学竞争不能仅靠替换考试名称完成，需重新考虑人物年龄、入学路径、经济压力和冲突发生场所。

### 21.3 两个轻量经验库

Trope条目：ID、关系机制、情绪承诺、成立条件、失效方式、目标受众假设、来源与实际实验ID。

Beat条目：ID、输入状态、人物行动、状态变化、读者回报、依赖条件、原创示例。所谓“强留存潜力”必须标为编辑判断；无实测证据时不能填为效果数据。

首轮只积累当前作品用到的条目。多个来源的拼接也需重新设计完整人物因果，不设“混合几本书即可通过”的规则。

## 22. 巴西角色与生活真实性

### 22.1 角色卡新增字段

- 社会资源：收入与生活来源、职业阶段、居住条件、家庭或社交支持。
- 权力来源及限制：金钱、职业、身份或信息如何影响具体行动，什么事情仍做不到。
- 关系边界：可接受与不可接受行为，越界如何改变选择与信任。
- 主动性：本阶段主动做出的关键选择、可替代方案、承担的代价、造成的结果。
- 声音：年龄、地区、职业、亲疏关系如何影响对白，避免所有角色同一种口语。

男主的危险性与专一程度是人物设计维度；女主的拒绝必须产生叙事后果。角色可以脆弱或受困，主动性不等于永远强硬，也不要求每章获胜。

### 22.2 真实性核查

cultural-recasting记录：事实ID、相关场景、设定、依据或母语编辑反馈、核查日期、可信度、影响范围。涉及关键职业、教育、住房、医疗或司法行为时，在采用前核查对应事实；不以笼统的“巴西人会这样”作为依据。

场景首次涉及重要本地机制时检查一次；每5章及Arc复盘检查整体一致性。虚构城市与幻想世界也需内部自洽，并分清虚构规则与现实参照。巴西背景不等同于贫民区、黑帮或某一种家庭模式。

葡语正文不必等到大纲第3版才启动。角色、世界与本章结构通过检查后即可试写；先用短对白检验语言规范，降低晚期整体返工。

### 22.3 门禁接入

G1检查文化核查缺口是否影响本章；G2检查人物主动选择与社会资源是否合理；G4检查对白语域和生活感。关键行动依赖不成立的现实机制时属于阻断问题，局部自然度由语言编辑处理。

高频表达只作为检查线索，不建立一律删除的词语黑名单。葡语中的正常对白标点也不能因为出现在“AI味”讨论中而被统一删除。

## 23. 开篇、节拍与承诺兑现

前5章试运行增加 opening-review，记录以下问题及原文位置，可直接放入review文件：

1. 核心困境和情绪承诺何时变得清楚？
2. 主要关系何时出现有效碰撞？
3. 女主何时作出改变局势的选择？
4. 读者已得到什么回报，还在期待什么？
5. 删掉某场景后，人物行动或理解是否完全不变？

节奏优化分两种：启动慢时，压缩无因果作用的准备场景并提前展示关系信号；重复多时，删除不改变状态的同类误会。压缩后必须复查动机和时间线，不能以提前揭底代替提速。

每章记录Hook类型、承诺内容、兑现依赖与本章Reward。结尾安静不自动失败；只有悬念没有回报、连续反复同一种阻碍、或宣传与正文承诺不同才需要重点处理。

正文按原创场景与阅读节奏切章，不保留参考作品章节对应关系。切章改变后更新ID映射、伏笔窗口、摘要与实验版本；不能将两个不同长度的“第3章留存”直接等同。

## 24. 内容与增长实验闭环

### 24.1 假设登记

hypotheses每条记录：假设ID、受众、产品与渠道、提出原因、证据类型、预测指标、反证条件、关联实验、状态与日期。

证据类型区分：外部观察、编辑判断、小样本定性反馈、本站实验。假设状态为proposed、testing、supported-in-scope、inconclusive或rejected。得到局部支持仍保留适用范围，不升级成所有巴西女性的普遍偏好。

### 24.2 分阶段实验

| 阶段 | 比较对象 | 控制与限制 |
|---|---|---|
| 概念筛选 | 最多3张不同关系发动机的Concept卡 | 作为定性筛选，不归因某个单独标签 |
| 单作品生产 | 胜出的一部前5章 | 验证流程、文化与阅读体验 |
| 包装测试 | 同一作品的标题或封面版本 | 每轮尽量只改一类变量，正文保持同版 |
| 开篇测试 | 同一定位的开篇修订版本 | 记录流量来源、展示条件和正文版本 |
| 商业测试 | 可控条件下的产品与付费设置 | 先核查渠道权限、规则与可获得指标 |

不默认20本并行，不做8变量全组合。不同作品、投放时间或渠道带来的结果差异，通常不足以证明某个人设造成了效果。

experiments最小字段：实验ID、假设ID、作品/素材版本、变量与对照、受众、渠道、时间窗、分配方式、主指标、护栏指标、样本量、结束条件、结果与下一步。

试验前确定结束条件，避免看到短期好结果就提前宣布胜出。自然流量不能随机分配时标注为观察性比较。样本不足时报告数量和方向，不宣称最佳方案。

### 24.3 素材承诺映射

creative-map记录标题/封面/短视频素材ID、表达的关系承诺、对应正文场景、是否涉及剧透、目标展示位置与版本。

同一本书可以有多种获客素材，但各素材必须对应真实故事。初期每个Concept先写少量一句话Hook，用来检查卖点是否清楚，不因暂时写不出20条就判定故事失败。

网文缩略图、社媒内容和整本书封面分别记录用途与效果。预算不足时优先测试一个入口，不强制生产两套完整视觉体系。素材生产与实际对外发布是不同步骤，本轮仅设计其接口。

### 24.4 指标口径

| 指标 | 必须记录的分母与限制 |
|---|---|
| CTR | 同一入口的点击/曝光；不以累计阅读量代替 |
| 第1章启动率 | 进入第1章人数/可追踪落地访客；无法关联时不计算 |
| 第3章完成率 | 同批第1章启动者中完成第3章的比例；固定观察窗及章节版本 |
| 付费墙到达率 | 到达付费墙人数/同批阅读启动人数 |
| 付费转化率 | 明确按到达付费墙者或阅读启动者计算，不能混用 |
| 付费后留存 | 同批首付费者中继续达到指定付费进度者比例 |
| 观察期每读者净收入 | 同批可归属净收入/读者数；注明时间窗、退款与费用口径 |

平台缺少事件、分母或归因时记为不可观测。聚合收入不应硬分摊为某个标题或Hook的收益。

转化率×平均购买章节数×平均每章净收入只可作为条件一致时的简化观察期估算，不能直接称为完整LTV。订阅、整本购买、价格差异及尚未结束的读者生命周期需采用各自口径。短期试验主要看可观测阅读与收入，不推断最佳终身篇幅。

### 24.5 数据回写权限

读者反馈进入feedback与hypotheses，经负责人和故事编辑复盘后，形成decisions中的新提案。不得自动覆盖角色卡、已定稿事实或结局。

CTR高而阅读低，先核查素材承诺和入口匹配；阅读低还需区分加载、章节长度、流量人群和内容问题。母语编辑负责语言诊断，目标读者试读负责阅读体验，两种反馈分开记录。

## 25. V0.3 试运行交付与检查

在已有前5章闭环之外增加四份轻量文件：market-brief、cultural-recasting、hypotheses、creative-map；真正开始读者测试时再维护experiments。共用Trope与Beat库按当前作品需要增长。

验证场景：

- 来源只有简介时，研究卡不会声称完成全文分析。
- 文化修改改变人物行动条件时，角色与场景同步修订。
- 角色更换职业后，资源和行为不继续沿用旧职业假设。
- 宣传承诺在正文没有依据时，素材退回修改。
- CTR上升但阅读指标下降时，不直接宣布素材胜出。
- 无法获得平台留存事件时，结果记为不可观测。
- 读者反馈建议改情节时，先形成提案，再走既有变更协议。

上述均为待执行的验收设计。当前没有样章、真实受众数据或商业实验结果，不以文档完善程度作为市场验证。

## 26. 本轮范围与后续决策

本轮完成架构优化，保留单作品前5章试运行规模。暂按巴西18—24岁女性进行设计；没有选择某部中文小说作为改编母本，也没有指定某个平台或固定付费点。

真正进入作品立项时，需要选定一个关系发动机、现实或幻想背景，以及优先验证的产品形态。可从重逢与长期专一、复仇与危险盟友、敌对关系与幻想世界中选择候选；它们来自讨论中的选题假设，尚无本项目数据证明优劣。

框架更新无需等待这些选择。首部作品的具体设定与生产计划应在立项时明确，避免提前为未选定类型维护大量资料。
